# Cloudflare caches static assets and ignores `no-store`

Prod sits behind Cloudflare, which caches by **file extension**: a `.js` or `.css` response is stored at the edge for hours regardless of what `Cache-Control` the origin sent. Verified in prod — `/lib/state.js` leaves the origin with `no-store, no-cache, must-revalidate` and comes back `cf-cache-status: HIT`, `Age: 56796`, its `Cache-Control` rewritten to a `max-age`. HTML is passed through (`DYNAMIC`), so only assets are affected. **Never reason about production asset caching from the origin's headers — read `cf-cache-status` / `Age` off a real response.**

Two consequences, both of which have already cost an outage:

- **Every asset URL the browser fetches must be path-versioned** — `/v/<BUILD_VERSION>/lib/ui.js`, never `/lib/ui.js` or `/lib/ui.js?v=…`. A new build asks for URLs no cache has seen, which is what makes a deploy self-healing. The single rewriter is [asset-versioning.ts](../src/web/asset-versioning.ts); both HTML shells go through it. **A `?v=` query string is not a substitute**: it is not part of the base URL an ES module's relative import resolves against, so it versions the entry point and *none* of its imports — and Cloudflare may key on path alone anyway. Only rewrite the entry-point `<script src>`; the prefix rides into the whole import graph for free. `tests/config/public-share-assets.test.ts` pins this.
- **Never put a static file behind auth.** Every script, stylesheet and image is served to anyone by [frontend-assets.ts](../src/web/frontend-assets.ts), mounted ahead of everything gated; the auth boundary is `/api` and the HTML shells. **`denyCaching()` does not make a rejection unstorable at Cloudflare** — it was believed to, and it doesn't. A probe on 2026-10-16 (a random, never-used `/v/<build>/zz-probe.js`, no cookie) came back `302`, `MISS`, then `HIT` on the next request, held ~22h. `denyCaching()` still goes on every rejection for browsers and other caches, but the only real defence is that an asset URL never answers with a rejection. `tests/web/security/frontend-assets.test.ts` pins it. The gate never protected anything anyway: the repo is public, and the edge was already handing its cached 200 `app.js` to logged-out visitors.

Two outages came out of that second point. First, `lib/mobile-rows.js` was missing from the old share-page allowlist (`PUBLIC_SHARE_ASSETS`, now deleted), Cloudflare cached the redirect against the bare URL ~4 minutes before the fix deployed, and every public share link rendered blank for 18 hours. Second, in Oct 2026, a logged-out request for a gated `/v/<build>/` module pinned the redirect at one Cloudflare location, and the authenticated app rendered an empty shell after a good login for everyone routed there. It surfaced as "broken on my phone, fine on desktop": **each Cloudflare location caches independently, and the cache key does not vary by device**, so a phone abroad and a desktop at home were simply asking different caches. A failure only one device or place sees, with login working, is this signature.

**When a shipped fix "doesn't work" in prod, check the edge before re-reading the code.** `curl -sD - <url> | grep -iE 'cf-cache|age|cache-control'` — an `Age` larger than the time since deploy means you are not talking to the app. **Probe with a random URL nobody uses, never a real asset**: a logged-out request for a real asset URL is exactly what poisons it. Any deploy heals a poisoned entry, because the build fingerprint in every asset URL changes.
