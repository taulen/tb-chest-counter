# Tin Man scores (Events → Ancients)

Rise of the Ancients standings, pasted in by an admin after each summon. The card sits on the Ancients tab and follows the selected run. Code: [tinman-repo.ts](../src/data/repositories/tinman-repo.ts), [tinman-parse.ts](../src/data/tinman-parse.ts), [routes/tinman.ts](../src/web/routes/tinman.ts), [tinman-scores.js](../src/web/public/pages/tinman-scores.js).

- **The in-game ranking is cumulative.** It never resets between summons, so each paste is a full snapshot. A player's points in a summon are the step from their previous pasted snapshot. Someone missing from a later snapshot keeps their last total.
- **A missed summon is fine.** If summon 2 is never pasted, its points land on summon 3. The table shows S2 as "not uploaded" and S3 as "incl. S2". Re-pasting a summon replaces it, and deleting one moves its points to the next pasted summon.
- **Runs are keyed by their Tinman day,** the Rise of the Ancients game day and the run's last day. `/api/events/ancients/occurrences` carries it as `tinmanDate`. With the feed down, the newest Tinman day on the 6-day cadence is used.
- **Name matching follows the might capture's `resolveMember` order.** Player merge rules come first (exact only), then every exact pass on name, alias and despaced key across active and inactive members, then fuzzy matching with active members first. A member can be claimed once per paste, and the exact match wins.
- **Nothing creates a member.** An unknown name stays unknown until an admin assigns it under *Names to check*. An assignment applies to the whole run and records the spelling as the member's alias, so future runs match exactly. "Not a clan member" on a fuzzy guess sticks for the run's later pastes.
- **Storage** (v80): `tinman_uploads` holds one row per clan, day and summon, with the uploader stored as a username. `tinman_scores` keeps the pasted name next to the matched member. The `member_id` FK is SET NULL on delete, so the row falls back to its pasted name. A player merge repoints it, and clan delete and clan restore handle both tables.
- **Targets** (v81, `tinman_targets`, one per clan and run): an admin pastes the Ancient planner's *Points per member* card. Its "points each" per tier and its "For N kills" line are kept.
  - Each player is held to their tier's target: their estimated guards level, or G7 when unknown, never T9.
  - The target is always the whole run's, never split per summon: the clan judges the total, so mid-run everyone simply reads as not there yet. The kill count is kept for display only.
  - The goal colours (`goalStatusClassFor`: green at target, amber from 66%, red below) and their glyph + words are the Leaderboard's.
  - Players under target are listed in *Below Tin Man target* at the bottom of the page.
- **Formats** the parser reads (one parser for every event below): markdown tables, tab-separated rows, CSV (`1,Name,"63,965,364"`, unquoted, or `;`-separated), and plain `rank name points` lines. Plain lines may separate name and points with `-` `–` `:` `=` `,`, end in "points"/"pts", carry markdown bold, or lead with a medal instead of a rank. Points can use any thousands separator, but only one kind per number, so a name ending in a digit keeps it (`Fiin SK 3 239,421`). In CSV the name is its own field, so `10,Fiin SK 3,239,421` reads as "Fiin SK 3" even unquoted. Lines it can't read are reported back, never dropped silently.

## Per-day scores (Events → Olympus, Ragnarok, Dark Omens)

Trials of Olympus (days 1–5), Ragnarok (days 1–2) and Dark Omens (days 1–2) use the same card, storage and matching, per **day** instead of per summon. Their sentences are shared: `dayEvent()` in [tinman-scores.js](../src/web/public/pages/tinman-scores.js) builds all three, so only the name and the API differ (plus any sentence passed as an override). The day count is `SCORE_EVENTS` in [tinman-repo.ts](../src/data/repositories/tinman-repo.ts), and the router is built with the event's `eventKey`. Adding another per-day event means one line in each of those, its key in `SCORES_EVENT_KEYS` (events.js), the occurrences route in api.ts and the mount loop in server.ts, plus its three audit labels.

- **v90 added `tinman_uploads.event_key`** (`ancients` for every older row), and the one-upload rule is per clan, event, run day and round. Every repo function takes the event key and defaults to `ancients`, so callers that only mean Ancients (the player profile) are unchanged. In the tables, `tinman_date` is the run's key and `summon` is its round, whatever the event.
- **Runs are keyed by their FIRST game day.** `/api/events/<event>/occurrences` carries it as `scoresDate`; Ancients carries `scoresDate` too, equal to its `tinmanDate`. The last day can't be used: it is in the future for most of a live run, and the route refuses future days.
- **Dark Omens pastes its Spoils of Dread damage ranking.** The card is titled "Spoils of Dread damage" and the view tab reads *Damage*, because the event's other measure, Omen Essence donated, already sits in the Essence column under *Participants* (resource tracking, not a paste). Both feed Tools → Rewards ([rewards-tool.md](rewards-tool.md)).
- **API:** `/api/event-scores/olympus`, `/api/event-scores/ragnarok` and `/api/event-scores/dark-omens`, the same paths as `/api/tinman` (a "summon" in the path is the day). There are no targets, no guards tiers, and no cadence warning. With no `?date=`, it shows the newest pasted run.
- **Assumed cumulative**, like Ancients: each paste is the ranking as it stands after that day. If the in-game ranking ever turns out to reset per day, the per-day columns would read as negative steps.
- Audit actions: `<event>_upload`, `<event>_delete`, `<event>_assign` (e.g. `olympus_upload`, `dark-omens_upload`).
