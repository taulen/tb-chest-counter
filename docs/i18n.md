# Translations (i18n)

The web UI ships in English (the default, always), Spanish, French, Russian and German. The runtime is [lib/i18n.js](../src/web/public/lib/i18n.js); the dictionaries are [lib/i18n/{es,fr,ru,de}.js](../src/web/public/lib/i18n/).

## How a string is translated

- **The English text is the key.** `t('Leaderboard')` returns the dictionary entry for `'Leaderboard'`, or the English when there is none. Interpolate with `{name}` placeholders: `t('Deleted {name}', { name: esc(name) })` — t() never escapes, so escape the values exactly as the English template did.
- **Plurals go through `tn()`**: `tn(count, '{n} chest', '{n} chests')`. The dictionary entry is keyed by the plural and holds the language's forms — Russian needs `one`/`few`/`many`, the others `one`/`other`. Never hand-roll `count === 1 ? … : …` in UI text.
- **Only string literals** go into t()/tn() — no variables, no `${}` templates. The build parses them; anything else fails the guard.
- **Whole sentences**, never concatenated fragments: word order differs between languages. Markup with attributes goes in a placeholder, not in the key.
- **Static markup in the HTML shells** uses `data-i18n` (the element's text) and `data-i18n-attr="title aria-label"` (those attributes). i18n.js translates them on load.

## Game names: `tGame()`, the game's own text

Chest names and sources, events, resources, items, titles, captains, artifacts, equipment, techs and their trees are the game's words, and a player matches them against their own game client. `tGame(englishName)` shows the game's **own** text for them in the chosen language — from the game's translation files, the same CSVs its client downloads — and the English otherwise. A plausible translation that isn't the game's own is worse than English: it sends someone looking for a name that doesn't exist.

Use tGame() only where a name is displayed — never in data-* attributes, URLs, select values, sort keys or anything sent back to the server. The data itself stays English: scans store the game's English names.

**Where the names come from** ([game-texts.ts](../src/game-protocol/game-texts.ts), built with names.json — [game-protocol.md](game-protocol.md#names-static-data)):

- Once per game patch the names build runs the static tables with the English CSV behind a lookup that records every translation key it reads, then again per language (`csv_de_DE`, `csv_es_ES`, `csv_fr_FR`, `csv_ru_RU`) with that language's CSV — only those keys kept — in front of the English. The two results are walked side by side, and every string at the same position is an English → localized pair. Templated names ("Level %value% epic Crypt") therefore come out concrete on both sides, in the game's own word order; pairs whose numbers agree become `{n}` patterns (`'Level {n} epic Crypt'` → `'Epische Gruft Level {n}'`) and the exact names a pattern reproduces are dropped.
- UI words the build never reaches — clan ranks, the Hall of Fame and Dragon labels, troop groups, a few event names, the Temple — come by translation key: `UI_TEXT_KEYS` in game-texts.ts, each pinned to the English the site passes to tGame. A key whose English changes in a game patch is logged (not alerted) by the build.
- One English text the game words two ways (it does: "Research speed" has two German wordings): the most frequent wins. Quotes become the language's own („…“, «&nbsp;…&nbsp;», «…»), because tGame's output lands in HTML attributes. Strings without a letter ("---") and anything with markup are left out. A key a language lacks stays English.
- Cached as `texts-<lang>.json` beside names.json (~3,200 entries, ~170–185 KB a language in Nov 2026) and served by `GET /api/game-texts/<lang>` ([routes/game-texts.ts](../src/web/routes/game-texts.ts)): public, because the login and share pages show names too; an `/api` path without an extension, so Cloudflare passes it through ([cloudflare-caching.md](cloudflare-caching.md)); `private, max-age=600` plus an ETag. A request never downloads anything — it only lets the server check for a game patch in the background, at most every ten minutes.
- i18n.js asks for it alongside the language's dictionary. The shell is translated and shown without waiting for it, but every importer of i18n.js does wait (top-level await), so no page renders a name before it is in and tGame stays synchronous. No texts yet, offline, or slower than 2.5 s: the names show in English (or the hand block's) and the page renders as before.

**Lookup order:** the game's text — exact, a `{n}` pattern, then the same after normalizing case, spacing, "Lvl" and dash style (the scan's own rule, [gift-text.ts](../src/game-protocol/gift-text.ts): the OCR era's stored "Lvl 25-29 Vault of the Ancients" finds the game's "Level 25–29 …") — then the hand `game` block, the ui dictionary (how the event catalog's own labels like 'Finish Reward' get translated), a hand `{n}` pattern, and the English.

**The hand `game` block** in `lib/i18n/<lang>.js` keeps only names the game's files don't cover: the app's own shorthands for events ("Ancients", "Olympus", "Runics", "Heroics", "Triumphal", "Ragnarok") and words the game never writes on their own ("Vault", "Citadel", "Clan Chest", "Gold Pass", "Engineering", "Player's portal", "Triumphal Challenge" without its "!") — 13 per language. Until Nov 2026 it held ~1,000 names per language copied in by hand, 67 of which (across the four languages) differed from the game's own wording; the game's text now wins over it. The guard (`tests/config/i18n-dictionaries.test.ts`) keeps it the same list in every language, small, and clear of `UI_TEXT_KEYS`. A missing UI word the game does have belongs in `UI_TEXT_KEYS`, never here.

## The choice, and where it lives

- Like the theme: localStorage (`lang`) for this browser, plus `users.language` (v89) for a signed-in account so it follows the person. `''`/null on the account = never chosen; the browser's choice is then adopted on sign-in (`adoptAccountLanguage`). The server's value wins when set.
- English is the default whatever the browser says — no `Accept-Language`, no `navigator.language`.
- **A change reloads the page.** Strings are baked into rendered HTML and module-level constants; a reload is the only way to re-render all of them.
- Pickers: the user menu and the phone drawer (signed in), next to the theme select on the public share page, and under the login form.
- **No English flash**: an inline bootstrap in `index.html`, `login.html` and `public-share.html` hides the page for a saved non-English language until i18n.js has translated the shell, with a 2.5 s CSS reveal as the safety net. The three copies are kept identical by `tests/config/i18n-bootstrap.test.ts`.
- i18n.js loads the dictionary with a top-level `await import()`, so every importer can call t() at module level. A dictionary that fails to load falls back to English; it can never take the module graph down.

## Adding or changing a string

1. Wrap it in t()/tn() (or `data-i18n` in a shell).
2. Run `npx tsx scripts/i18n-sync.ts missing out.json` for the work list, translate, and merge with `npx tsx scripts/i18n-sync.ts merge <lang> <file.json>` (it also drops entries the source no longer uses and keeps the files grouped by source file).
3. `npm run build` — `tests/config/i18n-dictionaries.test.ts` fails on any untranslated or stale entry, a placeholder or HTML tag that differs from the English, a bare `"` (it would end the attribute the string sits in), or a missing plural form.

Changing English text changes its key: every language needs the new entry, and the old one is reported stale.

German and Russian run 30–60% longer than English, and several tables lock their column widths. For anything layout-sensitive, the `local-ui-check` skill ([.claude/skills/local-ui-check/SKILL.md](../.claude/skills/local-ui-check/SKILL.md)) runs the dashboard locally on a sanitized copy of the newest backup and screenshots every page in all five languages at desktop and phone widths, flagging overflow and clipped text relative to English.

## Not translated

- Server messages (API errors, System-page log entries, Discord posts) are English. The login page maps its few known server errors.
- The setup wizard (a one-time operator flow) is English.
- Numbers keep the browser's formatting (`toLocaleString()`), dates stay ISO, year first. Month and weekday names follow the chosen language.
